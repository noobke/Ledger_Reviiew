1目标、约束与质量属性

1.1 架构目标

  1. 一条主链路可恢复：导入 → 拆页 → 分类 → 抽取 → 关联 → 审查 → 导出；任一步失败可重试，已完成页不重跑。
  2. 结论可回溯：每条问题都能追到页、区域、模板版本、规则版本、模型版本与人工操作。
  3. 原件零修改：输入只读，所有产物落在工作区；导出为单页 PDF，不二次加工原页内容。
  4. 可扩展而不暴露复杂度：新增表单 = 新增模板包；用户界面永远只有“导入、看结果、导出”。
  5. 离线可用：运行期不访问互联网；模型、字体、静态资源全部随包分发。

1.2 硬约束

约束现状架构应对
目标机无开发环境仅有 .NET 9 运行时；无 Python、Node、数据库采用 .NET 9 + 自包含发布（win-x64），目标机无需安装运行时；前端不用 npm 构建
开发机缺 SDK本机只有运行时，没有 .NET SDK开发前安装 .NET 9 SDK（winget）；CI/构建机需联网还原 NuGet
扫描件无文本层样本每页为 1 张 2279×3177 图像以图像为主：PDFium 渲染 + OCR + 视觉检测；PDF 原生文本仅作补充
手写与盖章勾选、姓名、日期、运行次数均手写字段级置信度 + “无法辨认”三态；不追求全字段自动数字化
单体离线单用户、单机本地进程 + 回环地址；预留服务化接口，但不实现多用户
大文件与批量单册 20–80MB、40–50 页；未来可能上千页流式渲染、页级任务、并行度受控、断点续跑、磁盘配额提示

1.3 质量属性优先级

属性场景指标
正确性拆页与分类页不丢不重；清晰件分类 ≥98%
可恢复性处理中途断电/崩溃重启后续跑，不重复计问题、不重复导出
性能100 页单册4 核 CPU ≤10 分钟；单页失败不影响整批
可维护性新增表单类型只改模板包与测试样本，不改主流程代码
可观测性定位误判任一结论可在 3 次点击内看到证据与版本信息

2关键决策（ADR）

#决策理由代价 / 风险
D1本机 Web：ASP.NET Core 仅监听 127.0.0.1，浏览器作界面界面表现力好、开发快；无需 Electron/WinForms；单机仍成立需管理端口与单实例；需防本机其他程序访问（随机端口 + 会话令牌）
D2.NET 9 + 自包含发布目标机已有运行时；自包含消除安装依赖；C# 生态满足 PDF/OCR/图像需求包体较大（约 150–250MB，含原生库与模型）
D3SQLite 单文件 + WAL零部署、可备份迁移、支持断点续跑与查询单写者；需任务串行化，避免并发写冲突
D4页级任务 + 幂等键大册可并行、可恢复；单页失败隔离需要严格的去重与状态机
D5模板包驱动（JSON + 基准图），不做用户可视化配置新增表单成本低、用户零配置；避免旧版 10 步配置实施人员需掌握模板包工具
D6签名三态 + 人工兜底手写签名自动判定无法保证 100%，三态最诚实需要人工确认界面与阈值校准流程
D7导出只做单页 PDF，不改原页内容保留原始扫描质量与证据价值；实现简单可靠不能“顺手修图”；导出件与原册页完全一致
D8前端零构建（原生 ES Modules + CSS），资源本地化开发机无 Node；离线要求禁止 CDN工程化程度低，需要自建组件与规范

3总体架构

逻辑上分五层。上层只依赖下层的接口，视觉与审查互不污染：识别错不该让规则“看起来通过”，规则调整也不应触发重新识别。

4运行与部署视图

4.1 进程模型

LedgerReview.exe（启动器，单实例互斥）
  └─ 选择空闲端口（默认 127.0.0.1:随机）
  └─ 启动 ASP.NET Core（Kestrel，仅回环地址）
  └─ 生成一次性会话令牌 → 拼到 URL → 打开默认浏览器
  └─ 托盘图标：打开界面 / 暂停任务 / 退出
  └─ 后台任务宿主：固定并发（CPU 核数-1，上限 4）

浏览器（Edge / Chrome）
  └─ 静态资源由本地服务托管（无 CDN、无外部字体）
  └─ 通过 REST + SSE 获取进度与结果

单实例保证同一工作区不被两个进程同时写。若检测到工作区位于网络共享盘，启动时告警并拒绝写入（SQLite 在共享盘上易损坏）。

4.2 工作区目录

工作区/
  ledger.db                 SQLite 主库（WAL）
  config.json               工作区配置（端口、并发、阈值覆盖）
  templates/                模板包（按版本分目录）
  signature-book/           字迹表版本与参考签名切片
  models/                   OCR / 签名模型（ONNX）
  batches/
    {batchId}/
      source/               原件只读副本（按 sha256 命名）
      pages/                页图 JPEG（200–300 DPI）+ 缩略图
      crops/                证据裁剪小图
      export/               导出的单页 PDF（按目录归档）
  logs/                     按天滚动
  backup/                   工作区备份（zip）

原件副本只读并记录 sha256；即使原件被移动或删除，批次仍可复现。页图与裁剪图可清理，数据库与导出件不可自动清理。

4.3 发布与升级

  • dotnet publish -c Release -r win-x64 --self-contained true，输出到 dist/；用 zip 分发。
  • 目标机：解压 → 双击 LedgerReview.exe → 选工作区 → 可用；不需要管理员权限。
  • 升级：替换程序目录，保留工作区；启动时执行数据库迁移（向前兼容，失败则回滚并提示）。
  • 模型与模板包分离：基础包不含大模型时，签名归属降级为“仅漏签”，OCR 仍可用。

5数据模型

18 张表，围绕“页 → 单据 → 事件 → 档案”和“问题 → 复核”两条主线。所有业务表带 created_at，结论表额外带版本三元组。

分组表说明
批次与文件Batch、SourceFile批次状态、文件指纹、页数、解析结果
页与单据Page、Document页图路径、质量分、旋转；单据类型、置信度、事件归属
档案与事件Equipment、Station、ServiceEvent一梯一档；事件键（设备+日期+第 N 次+类型族）
字段与观测FieldValue、CheckItem字段值/置信度/区域；检查项结果（✓/○/×/N/A/空）
签名SignatureSlot、SignatureMatch、SignatureRef应签位置、比对结果（三态+分数+候选）、字迹表参考样本
审查Finding、ReviewAction问题（规则、严重度、证据、版本）；人工确认/误报/待查
配置与运行TemplateVersion、SignatureBookVersion、Job、AuditLog模板与字迹表版本；页级任务与幂等键；操作日志

5.1 关键字段与约束

表.字段约束/含义
Page(batch_id, page_no)唯一；page_no 从 1 开始，等于原 PDF 页序
Document(page_id)一对一（一页一单）；doc_type、type_confidence、status
ServiceEvent.event_keystation|equipment|date|seq|family 的规范化串，唯一
FieldValue(document_id, field_code)每单据每字段一行；raw_value、norm_value、confidence、bbox、source
CheckItem(document_id, item_no)结果枚举：OK_TICK、OK_CIRCLE、FAIL_CROSS、NA、BLANK、UNREADABLE
SignatureSlot(document_id, slot_code)应签位置；role（维保/客户/第三方）、required_count
SignatureMatch(slot_id, segment_no)切分出的每个签名；verdict（MATCH/NOT_IN_ROSTER/UNDETERMINED）、person_id、score、candidates_json
Finding(page_id, rule_code, rule_version)同页同规则同版本幂等；severity、evidence_bbox、crop_path、related_pages
Job(idempotency_key)sha256:pageNo:stage:templateVer:modelVer；状态、重试次数、错误码

重跑策略：按 page_id + rule_version 删除旧 Finding 再写入，避免“重跑后旧问题残留”。人工复核记录不删除，作为审计轨迹保留。

6处理流水线

6.1 阶段与契约

阶段消费产出失败策略
S1 Import文件路径Batch、SourceFile、Page（仅页序）单文件失败隔离；加密/损坏给出错误码
S2 RenderPage页图、缩略图、旋转角单页重试 2 次；仍失败标“渲染失败”，继续其他页
S3 Preprocess页图质量分、质量标签、纠偏角低质量不阻断，进入“无法辨认”候选
S4 Classify页图 + 模板包单据草稿、类型、置信度、候选低置信 → 未识别，仍生成单据草稿
S5 Extract单据 + 模板区域FieldValue、CheckItem、SignatureSlot字段级失败不影响其他字段；置信度落库
S6 Link单据集合ServiceEvent、Equipment、档案归属缺键 → 事件不成立，相关规则报“无法判定”
S7 AuditPageFacts / EventFacts / 组基线Finding规则异常隔离到规则级，不拖垮整批
S8 SignatureSignatureSlot + 字迹表SignatureMatch、Finding(E1–E5)模型缺失 → 只跑漏签，明确提示
S9 ExportPage + Document单页 PDF + manifest逐页幂等；失败列清单，可单独重试

S4–S8 以页/事件为粒度并行；S9 在用户触发时执行，不自动跑，避免磁盘暴涨。

6.2 幂等与恢复

idempotency_key = sha256(file) + ":" + page_no + ":" + stage
                  + ":" + template_version + ":" + model_version
  • 任务开始前写入 Job(running)；完成后 done；异常退出后，启动扫描 running 超过阈值（默认 10 分钟）的任务，重置为 pending。
  • 写库使用事务；Finding 先按 (page_id, rule_version) 删除再插入，保证重跑一致。
  • 批次暂停/继续不销毁中间结果；已完成页不会重复 OCR。

6.3 并发与资源

  • 并行度 = min(4, CPU 核数−1)；OCR 与图像处理共享一个信号量，避免内存峰值。
  • PDF 渲染按页流式处理，不整册解码进内存；单页渲染失败不影响后续页。
  • 大册（>500 页）自动降级：先生成缩略图与分类，再逐页深度处理；界面可先看进度。

7分类器

目标不是“识别任意表单”，而是把 12 类内置表单分对，并诚实标出“不认识”。三路证据独立计算，再加权融合。

证据方法适用失败情形
标题文字页面上半部 OCR，匹配关键词（“（半月）”“监督记录表”“Service Docket”等）与表单编号清晰印刷标题标题被裁切、模糊、手写覆盖
模板相似页图降采样 → 二值化 → 与模板基准图做归一化互相关；再用 ORB 特征做二次确认版式稳定、扫描质量正常旋转、缩放、表格被手写填满
版式指纹检测水平线/竖线数量、表格行列数、签字栏位置、检查项数量区分半月/季/半年/年等同族表单表格线断裂、扫描歪斜

融合与阈值

score(type) = w1 * titleScore + w2 * templateScore + w3 * layoutScore
默认权重：w1=0.5, w2=0.3, w3=0.2

accept  : top1 ≥ 0.80 且 top1 - top2 ≥ 0.15
candidate: top1 ≥ 0.55        → 标“未识别”，给 2 个候选
unknown : 其余                → 标“未识别”

权重与阈值放在配置中，可按批次质量整体缩放；所有阈值的调整必须有金标集回归记录。分类结果永远可人工切换，但切换只影响本批审查口径。

8.2 抽取策略

对象方法置信度与兜底
印刷文字OCR 行检测 + 识别；表单编号、检查项文字走白名单纠错字符置信度均值；低于阈值标“无法辨认”

8.3 归一化层

  • 日期：2026.7.21、2026年7月21日、2026-07-21、26.7.21 统一为 ISO 日期；两位年份按“不晚于当前年 + 合理跨度”推断。
  • 数字：全角转半角，O→0、l/I→1 仅在数字上下文中替换；运行次数允许千分位。
  • 设备号：去空格、统一连字符，保留原始写法；比较时用规范化值。
  • 姓名：只用于“签名与填写姓名是否一致”的辅助，不做严格匹配（手写姓名识别本身不可靠）。
不要做的事 不做整页 OCR 后“猜字段”；不把 OCR 文本直接当结论；不对低质量页做图像增强后“强行识别出值”。审查工具的价值在于“指出问题”，不在于“填满表格”。

9签名校对

这是技术风险最高的模块。设计原则：先检测、再切分、后比对；永远保留灰区与人工兜底；先做可评测的基线，再谈模型升级。

9.1 处理链

  1. 位置：模板包给出应签矩形；对矩形做墨迹检测（自适应二值化 + 连通域），判断“有/无”。
  2. 去干扰：红色印章走颜色通道分离（印章像素不计入签名墨迹）；表格线用形态学去线。
  3. 切分：多人签名框用水平投影 + 连通域聚类切成 N 段；切分不确定时标“无法切分”。
  4. 预处理：纠偏、裁剪留白、尺寸归一（如 128×256）、笔画归一；保留原图用于展示。
  5. 嵌入：ONNX 模型输出定长向量；模型不可用时降级为传统描述子（HOG + 投影 + 墨迹统计）。
  6. 比对：与该人 5 个参考签名逐一算余弦相似度，取 top-k 均值；得到每人分数。
  7. 判定：最高分 ≥ 接受阈值且领先第二名 ≥ 间隔 → MATCH；最高分 < 下限 → NOT_IN_ROSTER；其余 → UNDETERMINED。
  8. 多人指派：一个框里有 2 段签名时，用匈牙利算法做“段→人”的最优指派，避免两人都匹配到同一人。

9.2 与产品的对应

9.3 评测与阈值校准

  • 数据：当前 20 人 × 5 签名；每人留 1 个做测试、4 个做参考，轮换 5 次（留一法）。
  • 指标：Top-1 归属准确率、灰区比例、误配率（把 A 判成 B）、拒识率；按清晰/模糊分层统计。
  • 阈值：先用留一法画分数分布，取“误配率 ≤1%”对应的分数为接受阈值；灰区下限取“拒识率 ≤20%”对应分数。
  • 发布门禁：清晰签名 Top-1 ≥85%、误配 ≤1%；达不到则默认“只给候选 + 人工确认”，不开启自动判定。
  • 监控：每批统计灰区比例与人工改判率；连续偏高时提示“字迹表需补充样本”。
技术现实 公开研究（SigNet 类模型、GPDS 合成数据）在理想数据集上的等错误率可到 3%–7%，但本场景是“扫描件 + 中文手写 + 印章干扰 + 每人仅 5 个参考”，实际精度会明显低于论文数字。因此架构上必须默认“灰区 + 人工”，不能把自动判定当作唯一路径。

10关联与档案

10.1 键的设计

equipment_key = normalize(station) + "|" + normalize(equipmentId)
event_key     = equipment_key + "|" + date + "|" + seqNo + "|" + family
family        = CHUITI | FUTI | SUPERVISION | REPAIR | CONTROL
  • 设备编号为空时，用“文件名中的编号”或“同册多数编号”兜底，并标“关联不可靠”。
  • 监督记录表通常不写第 N 次：按 equipment_key + date(±1) 挂到最近的保养事件；同时挂多个事件时标“关联冲突”。
  • “一梯一档”在跨批次合并时生效：同设备编号的不同批次按时间轴排列，供 B2/B8 等时序规则使用。

10.2 冲突与缺件

情形处理问题

一个事件只有保养单，没有监督记录表标“缺监督记录”，按开关决定是否报C6 [TBD]

11审查引擎

11.1 规则契约

public interface IAuditRule {
    string Code { get; }            // 如 "A1"
    RuleScope Scope { get; }        // Page | Event | EquipmentSeries | StationGroup
    string Version { get; }
    RuleOutcome Evaluate(RuleContext ctx); // Hit / Pass / Undetermined + findings
}

三态结果是硬要求：Pass 表示“检查过且没问题”；Undetermined 必须带原因（缺上下文、数据不足、质量差），并在界面显示为“无法判定”，不能混进“通过”。

11.2 上下文

上下文内容典型规则
PageFacts类型、字段值、检查项、签名位、质量分A1–A5、B1、B6、C2、D1、E1
EventFacts同事件的保养单 + 监督记录表 + 签名归属B7、D3、E3、C5
EquipmentSeries同设备按日期/次数排序的序列B2、B3、B8、C1、C5
StationGroup同站同类型同 N 的多设备记录B4（需 ≥3 台）

11.3 同站基线（“找异类”）

用户口径：同站同一次保养的日期应一致，个别不一致的就是异类。实现不用“配置基准”，而用批内数据自洽：

  1. 按 station + family + period + seqNo 分组。
  2. 组内日期取中位数；计算每台设备与中位数的偏差天数。
  3. 偏差为 0 的占多数时，把非 0 的少数标为“异类”，附组内分布。
  4. 组内设备数 <3，或日期缺失过半 → 不作结论（Undetermined）。

这样既尊重“同站一致”的业务事实，又不需要用户维护任何基准表；规则失败时不会误报。

11.4 证据与幂等

  • Finding 存页号、归一化 bbox、裁剪图路径、规则版本、模板版本、模型版本。
  • 执行前按 (page_id, rule_code, rule_version) 清理旧结果；人工复核记录单独表，不受影响。
  • 规则异常（空引用、越界）被捕获为 RULE_ERROR 问题，提示“规则 X 执行失败”，不静默吞掉。
  • 严重度由规则定义，不允许运行期随意改；如需调整，改规则版本并回归。

12拆分与导出

12.1 单页 PDF 生成

  • 优先使用 PDF 库“导入单页到新文档”的能力（保留原始页面对象与图像压缩），避免“渲染成图再包 PDF”导致的二次损失。
  • 页旋转、裁剪框按原页继承；不添加水印、不压缩图像。
  • 导出前校验：新文档页数 = 1，页面尺寸与原页一致；失败则该页列入失败清单。

12.2 命名与目录

{station}_{equipmentId}_{docTypeName}_{yyyy-MM-dd}_P{pageNo:D3}.pdf

非法字符替换为下划线；总长度 > 180 字符时截断 docTypeName；
重名时比对内容：相同跳过，不同追加 _2/_3。

目录结构见 PRD 6.2；未识别 与 低质量 也单独成目录，确保“每页都有去处”。

12.3 导出清单

导出完成后在工作区写 export-manifest.csv（页码、原文件、单据类型、目标路径、结果），供核对；界面显示“成功/跳过/失败”数量。

15性能与容量

15.1 单页耗时预算（4 核 CPU，扫描件）

步骤预算说明
渲染（200–300 DPI）0.2–0.5 sPDFium；按需只渲染当前页的高分辨率图
预处理 + 质量0.1–0.2 s灰度、纠偏、去边
分类0.2–0.4 s降采样匹配 + 标题 OCR（可复用 OCR 结果）
OCR（整页）0.8–1.5 sPP-OCRv5 CPU；只对必要区域做二次识别
勾选检测0.1–0.2 s网格切分 + 形状分类
签名检测/比对0.2–0.5 s/位置嵌入 + 20 人比对
单页合计1.6–3.0 s100 页约 3–5 分钟（并行后）；加上排队与 I/O，目标 ≤10 分钟

以上为设计预算，需在真实样本上实测校准；若 OCR 成为瓶颈，先限制识别区域（只识别字段区与标题区），不要整页 OCR。

15.2 存储估算

  • 页图（200 DPI JPEG，质量 80）：约 300–500KB/页 → 10,000 页约 3–5GB。
  • 缩略图：约 20KB/页；证据裁剪：约 30–80KB/条。
  • 导出单页 PDF：与原始页数据量相当（不重压缩）；可与页图共用，不额外长期保留。
  • 启动时检查磁盘余量，低于 5GB 提示清理；可配置“批次完成后保留页图 N 天”。

17质量与评测

17.1 金标集

  • 从真实材料中抽取 ≥100 页，逐页人工标注：类型、关键字段真值、检查项结果、应签位置与签名归属、已知问题。
  • 签名另建留一法集：20 人 × 5 签名，轮换测试；后续补更多人与更多样本。
  • 金标集与代码同仓库管理（脱敏后），每次发布跑回归，输出混淆矩阵与指标表。

17.2 测试层级

层级内容门禁
单元归一化、几何换算、规则命中/不命中/无法判定、命名与冲突全绿；规则覆盖 100%
集成导入→导出全链路；断点续跑；重复导入幂等真实 5 页样本跑通
视觉回归分类与抽取在金标集上的指标不低于上一版；下降即阻断
性能100 页批量计时、内存峰值≤10 分钟；峰值 ≤2GB
交付干净目录解压启动、断网、中文路径一次通过

17.3 “无评测不上线”

任何新规则、新阈值、新模型，必须先在金标集上给出前后对比；没有数字的改动不得进入默认路径。旧版“规则空转、评测空转”的教训必须写进发布检查单。
